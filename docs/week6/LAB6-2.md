# Lab 6-2 — Sprint Review ของ Todo List

อ้างอิงโจทย์หน้า 160–163 | วิดีโอ 5–10 นาที | Feedback จริงอย่างน้อย 3 ข้อ

## 1. Sprint Goal

ผู้ใช้สามารถจัดการงานส่วนตัว ค้นหางานที่ต้องการ และกลับมาเปิดดูข้อมูลที่บันทึกไว้ใน browser เดิมได้

## 2. Completed / Not Completed ตามหลักฐาน

| งาน | หลักฐานที่มี | สถานะสำหรับ Review ของทีม |
|---|---|---|
| Todo CRUD / Complete / Persistence | โค้ด, tests และ browser automation จาก Lab 5-3 | โค้ดพร้อม Demo; รอ Manual Test และ Peer Review |
| ระบบสมาชิกและรหัสกู้คืนจำลอง | ทดสอบสมัคร เข้าระบบ แยกบัญชี และกู้รหัสผ่าน | โค้ดพร้อม Demo; รอทีมยืนยัน DoD |
| ธีม/ฟอนต์/ขนาด/Reset | component tests และฟอนต์ภายในโปรเจกต์ | โค้ดพร้อม Demo; รอทีมยืนยัน DoD |
| Search / Filter / Sort / Clear completed | tests และ browser automation | โค้ดพร้อม Demo; รอทีมยืนยัน DoD |
| Manual Test / Peer Review / Merge เข้า dev | มีคู่มือและ Draft PR #3 | ยังไม่มีผลยืนยันในชุดงานนี้ |

**Completed ที่ผ่าน DoD ของทีม:** ยังยืนยันไม่ได้จนกว่าจะมีผลตรวจจริง อย่าเปลี่ยนเป็น Done เพราะ tests ของ Codex ผ่านอย่างเดียว หลังทีมตรวจแล้วให้ย้ายรายการที่ผ่านไป Completed พร้อมชื่อผู้ทดสอบและหลักฐาน

งานต่อยอดที่ยังไม่ได้ทำและไม่ได้สัญญาไว้ใน Sprint เดิม ได้แก่ due date, priority, export/import และ sync ข้ามเครื่อง จัดเป็น Future Backlog ไม่ใช่สรุปว่า Sprint ล้มเหลวเพราะไม่มีฟีเจอร์เหล่านี้ ระบบสมาชิกเป็น frontend demo ไม่ใช่ backend หรือบริการส่งอีเมล

## 3. Demo ระบบจริง 6 ขั้น

| ลำดับ | สิ่งที่ทำบนหน้าจอ | ผลที่ควรเห็น |
|---|---|---|
| 1 Create | เพิ่ม “อ่านบทที่ 4 Black Box Testing” | มีรายการใหม่; ลองข้อความว่างแล้วต้องไม่เพิ่ม |
| 2 Edit | เปลี่ยนเป็น “อ่าน BVA และทำแบบฝึกหัด” | ข้อความเปลี่ยนโดยไม่เกิดรายการซ้ำ |
| 3 Complete | ติ๊กว่างานเสร็จ | สถานะและจำนวนงานเสร็จเปลี่ยน |
| 4 Filter | กรอง “เสร็จแล้ว” และค้นหา “BVA” | เหลือรายการที่ตรงทั้งสองเงื่อนไข |
| 5 Delete | ล้างตัวกรองและลบรายการทดลอง | รายการถูกลบตาม flow จริง |
| 6 Refresh | เพิ่ม “เตรียม Sprint Review” แล้วรีเฟรช | งานยังอยู่ใน browser เดิม |

ช่วงเสริม: สลับผู้เยี่ยมชม/บัญชีจำลองเพื่อแสดงการแยกข้อมูล และเปลี่ยนธีม หากเวลาไม่พอให้เน้น 6 ขั้นหลัก ไม่ใช้สไลด์แทน Live Demo

## 4. Feedback → Updated Product Backlog

**ต่อไปนี้เป็นข้อเสนอเตรียมคุย ไม่ใช่คำพูดที่ได้รับจาก Stakeholder แล้ว** ให้เพื่อนกลุ่มอื่นหรืออาจารย์ลองใช้งาน จากนั้นแทนที่ด้วย feedback จริงอย่างน้อย 3 ข้อใน [TEAM-EVIDENCE.md](TEAM-EVIDENCE.md)

| รหัสตัวอย่าง | ประเด็นเสนอคุย | User Story | Priority เสนอ | SP เสนอ | Acceptance Criteria |
|---|---|---|---|---:|---|
| FB-D1 → TD-08 | ต้องการรู้กำหนดส่ง | ในฐานะผู้ใช้ ฉันต้องการกำหนดวันส่ง เพื่อจัดงานก่อนถึงกำหนด | Must | 3 | เลือกวันได้; แก้/ล้างวันได้; refresh แล้วยังอยู่; งานเลยกำหนดที่ยังไม่เสร็จมีป้ายกำกับ |
| FB-D2 → TD-09 | งานสำคัญควรเห็นก่อน | ในฐานะผู้ใช้ ฉันต้องการระบุความสำคัญ เพื่อเลือกทำงานเร่งด่วนก่อน | Should | 2 | มีสูง/กลาง/ต่ำ; ค่าเริ่มต้นกลาง; เรียงตามความสำคัญได้; persistence ถูกต้อง |
| FB-D3 → TD-10 | กังวลข้อมูลหายเมื่อล้าง browser | ในฐานะผู้ใช้ ฉันต้องการส่งออกและนำเข้าข้อมูล เพื่อสำรองงานของตัวเอง | Should | 5 | export JSON ได้; ตรวจรูปแบบ import; แสดงผลก่อนยืนยัน; ไฟล์ผิดไม่ทับของเดิม |

Backlog หลังคุยจริงต้องบันทึกผู้ให้ Feedback, วันที่, ข้อความ, ID ของ Story และเหตุผลจัดลำดับ เช่น Due Date อาจสูงสุดเพราะช่วยลดการลืมส่งงาน แต่ต้องให้ Stakeholder ยืนยัน ไม่จำเป็นต้องทำทุกข้อทันที และไม่เพิ่ม search/mobile ซ้ำโดยไม่ตรวจของเดิม เพราะเวอร์ชันนี้มีแล้ว

## 5. Reflection ฉบับตั้งต้น

“จากหลักฐานโค้ดและการทดสอบอัตโนมัติ เรามี Todo List ที่พร้อมนำไปสาธิตฟังก์ชันหลัก แต่ยังต้องตรวจ Manual Test และให้เพื่อนทดลองใช้ก่อนสรุปว่า Sprint Goal สำเร็จตาม DoD ของทีม การ Demo ควรทำเป็นสถานการณ์ใช้งานต่อเนื่อง เพื่อให้ผู้ทดลองเห็นว่าจะใช้ระบบในชีวิตจริงอย่างไร ส่วนข้อเสนอใหม่ต้องจดเป็น Backlog และจัดความสำคัญก่อนเลือกเข้า Sprint ต่อไป”

หลัง Review ให้เพิ่ม: ใครทดลอง, เจอปัญหาขั้นไหน, Story ใด Completed จริง, Goal สำเร็จหรือไม่และเพราะอะไร, Feedback ใดสำคัญที่สุด ห้ามใช้ reflection ตั้งต้นแทนสิ่งที่ทีมได้เรียนรู้จริง
